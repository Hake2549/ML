# ช่วงที่ 1: Problem & Data Understanding (4 หน้า)

## หน้า 1 — Title
- ชื่อเรื่อง: **Hotel Booking Cancellation Prediction**
- ชื่อผู้จัดทำ 5 คน + รหัสนักศึกษา, รายวิชา, อาจารย์ผู้สอน

## หน้า 2 — ทำไมต้องทำนายการยกเลิก
- **หัวเรื่อง:** "ยกเลิก 37% = รายได้ที่หายไปและพยากรณ์ห้องผิดพลาด"
- ที่มา: ยกเลิกกระชั้นชิด → ขายห้องต่อไม่ทัน → ต้อง Overbooking ซึ่งเสี่ยง
- **Input** = ข้อมูลการจอง ณ วันที่จอง → **Output** = ยกเลิก (1) / ไม่ยกเลิก (0)
- ขอบเขต: โรงแรม 2 แห่งในโปรตุเกส ก.ค. 2015 – ส.ค. 2017
- 📌 ตัวเลขเด่น: **37%**

## หน้า 3 — ข้อมูลและความไม่สมดุลของคลาส
- **หัวเรื่อง:** "ทายว่าไม่ยกเลิกทุกรายการ ก็ได้ Accuracy 62.9% แล้ว"
- 🖼️ `outputs/figures/3_target_distribution.png`
- 119,390 แถว × 32 คอลัมน์ · ยกเลิก 44,224 : ไม่ยกเลิก 75,166
- **ประโยคสำคัญ:** "นี่คือเหตุผลที่เราไม่ใช้ Accuracy เป็นตัวชี้วัดหลัก" (ปูทางไปหน้า 11)

## หน้า 4 — ปัจจัยที่เห็นได้จาก EDA
- **หัวเรื่อง:** "ประเภทมัดจำและช่องทางการจองต่างกันชัดเจน"

# ช่วงที่ 2: Data Preparation (2 หน้า)

## หน้า 5 — ทำความสะอาดข้อมูลโดยเสียข้อมูลแค่ 0.15%
- **หัวเรื่อง:** "119,390 → 119,208 แถว (ลบเพียง 182 แถว = 0.15%)"
- 📋 ตารางย่อจาก `outputs/tables/4_preparation_log.csv` เลือกมา 4 แถว:
  `children` → 0 · `country` → Unknown · `agent`/`company` → flag · ลบแถวที่ไม่มีผู้เข้าพัก 180 แถว
- **เหตุผลที่ต้องพูด:** ค่าว่างใน `agent`/`company` ตามเปเปอร์แปลว่า "ไม่เกี่ยวข้อง" ไม่ใช่ข้อมูลหาย จึงทำเป็น flag ไม่ใช่เติมค่า

## หน้า 6 — Data Leakage และการแบ่งข้อมูล ⭐
- **หัวเรื่อง:** "ตัด 3 คอลัมน์ที่แอบรู้คำตอบ ก่อนแบ่งข้อมูล"
- ตัด `reservation_status`, `reservation_status_date`, `assigned_room_type`
- **หลักฐาน:** การจองที่ถูกเปลี่ยนห้องมีอัตรายกเลิก **0%** → แปลว่ารู้ผลหลังเช็คอินแล้ว
- 📋 ตารางแบ่งข้อมูล: Random (95,366 / 23,842) · Time-based (95,190 / 24,018)
- ทุกขั้นตอนอยู่ใน Pipeline → encoder เรียนรู้จาก train เท่านั้น

## หน้า 7 — สร้าง 9 Features ใหม่จากสมมติฐาน
- **หัวเรื่อง:** "ประวัติการยกเลิกเดิมแยกกลุ่มได้ต่างกันถึง 81.6%"

## หน้า 8 — คัดเลือกด้วย 3 วิธี แล้วโหวต
- **หัวเรื่อง:** "37 features → 18 features ด้วยการโหวต 2 ใน 3"
- 🖼️ วาง 3 กราฟเล็กเรียงกัน: `5_mutual_information.png` · `5_random_forest_importance.png` · `5_permutation_importance.png`
- 3 วิธีที่ใช้: **Mutual Information** (Filter) · **RF Feature Importance** (Embedded) · **Permutation Importance** (Model-agnostic)
- **จุดที่ทำให้ดูลึก:** RF Importance มีอคติเข้าข้างตัวแปรที่มีค่าหลากหลาย จึงต้องใช้ Permutation Importance ยืนยัน
- ผลโหวต: 3 โหวตเต็ม 14 ตัว · 2 โหวต 4 ตัว · รวมเก็บ 18 ตัว
- Top features: `deposit_type`, `agent`, `lead_time`, `country`, `is_domestic`, `total_of_special_requests`

## หน้า 9 — ผลก่อน–หลังคัดเลือก
- **หัวเรื่อง:** "ใช้ feature น้อยลงครึ่งหนึ่ง แต่ผลเท่าเดิมและเร็วขึ้น"

- **ประโยคสำคัญ:** "ผลต่างน้อยกว่าค่า std → ไม่ต่างกันอย่างมีนัยสำคัญ แต่ C มีความแปรปรวนต่ำที่สุดและเทรนเร็วที่สุด จึงเลือก C"

# ช่วงที่ 5: Evaluation & Hyperparameter Tuning ⭐ (4 หน้า)

## หน้า 11 — เลือก Metric ให้ตรงกับต้นทุนธุรกิจ
- **หัวเรื่อง:** "Accuracy หลอกตา — Dummy ได้ 62.9% แต่ F1 = 0"
- ตารางต้นทุน: **FN** = ห้องว่าง ขายต่อไม่ทัน (รายได้หาย) · **FP** = Overbooking ห้องไม่พอ (เสียชื่อเสียง)
- → เลือก **F1 เป็นหลัก** เสริมด้วย ROC-AUC และ PR-AUC

## หน้า 12 — ผลก่อน–หลัง Tuning
- **หัวเรื่อง:** "Tuning ช่วยลด Overfitting มากกว่าจะเพิ่มคะแนน"

| โมเดล | F1 ก่อน | F1 หลัง | ช่องว่าง Train–CV |
|---|---|---|---|
| LogisticRegression | 0.7629 | **0.7784** | 0.001 → 0.002 |
| **RandomForest** | 0.8422 | 0.8419 | **0.152 → 0.122** |
| HistGradientBoosting | 0.8112 | **0.8344** | 0.011 → 0.062 |

- **ประโยคสำคัญ:** "F1 ของ RF แทบไม่ขึ้นเลย แต่ช่องว่าง train–CV แคบลงจาก 0.152 เหลือ 0.122 แปลว่าโมเดลจำข้อมูลน้อยลงและมีเสถียรภาพมากขึ้น"
- 🖼️ `outputs/figures/7_validation_curve_rf_max_depth.png` ใช้อธิบายว่าเลือก `max_depth` จากตรงไหน
- ค่าที่เลือกใช้: `n_estimators=300`, `max_depth=30`, `min_samples_leaf=2`, `max_features='log2'`, `class_weight='balanced_subsample'`

## หน้า 13 — Threshold Tuning และผลบน Test Set
- **หัวเรื่อง:** "ปรับ threshold เป็น 0.46 เพิ่ม Recall ได้ 2.6 จุด"
- 🖼️ `outputs/figures/7_confusion_matrix.png` (หรือ `7_threshold_tuning.png`)
- 📋 ผลสุดท้ายบน Test 23,842 แถว: **F1 0.8469 · Precision 0.8351 · Recall 0.8590 · ROC-AUC 0.9567 · Accuracy 0.8849**
- ย้ำ: Test set ถูกใช้ครั้งเดียวตอนท้าย การเลือกทุกอย่างก่อนหน้าใช้ CV บน train เท่านั้น

## หน้า 14 — Random vs Time-based Split ⭐ (หน้าเด็ดสุด)
- **หัวเรื่อง:** "ถ้าทดสอบแบบทำนายอนาคตจริง F1 ตกจาก 0.847 เหลือ 0.725"

| วิธีแบ่งข้อมูล | F1 | Precision | Recall |
|---|---|---|---|
| Random split (t=0.46) | **0.8469** | 0.8351 | 0.8590 |
| Time-based split (t=0.46) | **0.7249** | 0.7996 | 0.6630 |

- **สาเหตุ:** ชุด test ตามเวลามีอัตรายกเลิก **40.99%** ขณะที่ train มี **36.09%** → พฤติกรรมเปลี่ยนตามเวลาจริง (distribution shift)
- **ประโยคปิด:** "การสุ่มแบ่งข้อมูลประเมินโมเดลสูงเกินจริง เราจึงรายงานตัวเลขทั้งสองแบบ"
