# 👤 คนที่ 2 — หน้า 5–9 ⭐

## หน้า 5: ทำความสะอาดข้อมูล
> "ในการทำความสะอาดข้อมูล เรายึดหลักว่า**เก็บข้อมูลไว้ให้มากที่สุด ลบเฉพาะที่เป็นไปไม่ได้จริง**
> ค่าว่างเราเติมแทนการลบแถว เช่น children เติม 0, country ใส่ Unknown
> จุดที่น่าสนใจคือ agent กับ company ที่ว่างเยอะมาก เปเปอร์ต้นฉบับระบุว่าค่าว่างตรงนี้**แปลว่าไม่ได้จองผ่านเอเจนต์ ไม่ใช่ข้อมูลหาย** เราจึงแปลงเป็น flag แทนการเติมค่ามั่ว
> ส่วนที่ลบจริงมีแค่การจองที่ไม่มีผู้เข้าพักเลย 180 แถว กับราคาห้องผิดปกติอีก 2 แถว
> รวมแล้ว**เสียข้อมูลไปเพียง 182 แถว หรือ 0.15%** และอัตราการยกเลิกแทบไม่เปลี่ยน"

## หน้า 6: Data Leakage ⭐
> "หน้านี้สำคัญมากครับ/ค่ะ เราตรวจพบ 3 คอลัมน์ที่ต้องตัดทิ้งเพราะเป็น **Data Leakage**
> `reservation_status` บอกผลลัพธ์ตรงๆ อยู่แล้วว่ายกเลิกหรือเช็คเอาท์ ส่วน `assigned_room_type` คือห้องที่ได้จริงซึ่งรู้ตอนเช็คอิน
> **หลักฐานคือ การจองที่ถูกเปลี่ยนห้องมีอัตรายกเลิก 0%** เพราะคนที่ยกเลิกไปแล้วย่อมไม่มีใครเปลี่ยนห้องให้ นี่ชัดเจนว่าเป็นข้อมูลที่รู้หลังเหตุการณ์
> ถ้าไม่ตัดออก โมเดลจะแม่นเกือบ 100% แต่ใช้งานจริงไม่ได้เลย
> จากนั้นเราแบ่งข้อมูล 2 แบบ คือสุ่มแบ่ง 80:20 ได้ train 95,366 กับ test 23,842 แถว และแบ่งตามเวลาอีกชุดหนึ่ง
> ทุกขั้นตอนการแปลงข้อมูลอยู่ใน Pipeline จึงเรียนรู้จาก train เท่านั้น ส่วน test เราเปิดใช้ครั้งเดียวตอนท้าย"

## หน้า 7: สร้าง Feature ใหม่
> "เราสร้าง feature ใหม่ 9 ตัว โดย**ตั้งสมมติฐานก่อน แล้วค่อยพิสูจน์ด้วยข้อมูล** ไม่ได้สร้างมั่วแล้วลองดู
> ตัวที่ได้ผลดีที่สุดคือ `cancel_history_ratio` หรือสัดส่วนการยกเลิกในอดีตของลูกค้า **แยกกลุ่มได้ต่างกันถึง 81.6%**
> รองลงมาคือช่วงระยะเวลาจองล่วงหน้า 58.1% และจำนวนคืนที่พัก 52.8%
> ตัวเลขนี้คือผลต่างของอัตราการยกเลิกระหว่างกลุ่มต่ำสุดกับสูงสุด ยิ่งกว้างแปลว่ายิ่งแยกคนที่จะยกเลิกออกจากคนที่ไม่ยกเลิกได้ดี"

## หน้า 8: คัดเลือก Feature ⭐
> "หลังสร้าง feature ใหม่ เรามีตัวแปรทั้งหมด 37 ตัว จึงต้องคัดเลือก
> เราใช้ **3 วิธีที่มาจากแนวคิดต่างกัน** คือ Mutual Information ที่ดูสถิติล้วน, Random Forest Importance ที่ได้จากตัวโมเดล และ Permutation Importance ที่สลับค่าในคอลัมน์แล้ววัดว่า F1 ตกลงเท่าไหร่
> เหตุผลที่ต้องใช้หลายวิธีคือแต่ละวิธีมีจุดอ่อนต่างกัน โดยเฉพาะ **Random Forest Importance มีอคติ ชอบให้คะแนนสูงกับตัวแปรที่มีค่าหลากหลาย** เราจึงใช้ Permutation Importance ที่วัดบน validation set เป็นตัวถ่วง
> เกณฑ์คือให้แต่ละวิธีโหวต Top 18 ของตัวเอง ตัวไหนได้อย่างน้อย 2 ใน 3 เสียงถึงจะเก็บไว้
> **ผลคือเหลือ 18 ตัว** แบ่งเป็นได้ครบ 3 เสียง 14 ตัว และได้ 2 เสียงอีก 4 ตัว"

## หน้า 9: ก่อน–หลังคัดเลือก
> "เราพิสูจน์ว่าการคัดเลือกไม่ทำให้ผลแย่ลง โดยทดสอบ 3 ชุดด้วยโมเดลเดียวกันและวิธีวัดเดียวกัน
> ชุด A ตัวแปรเดิม 28 ตัว ได้ F1 0.8103 ชุด B ที่เพิ่ม feature ใหม่เข้าไปเป็น 37 ตัว ได้ 0.8127 และชุด C ที่คัดเหลือ 18 ตัว ได้ 0.8112
> **ผลต่างระหว่าง B กับ C แค่ 0.0015 ซึ่งน้อยกว่าค่า std ที่ 0.0042** จึงถือว่าไม่ต่างกันอย่างมีนัยสำคัญ
> แต่ชุด C ใช้ตัวแปรแค่ครึ่งเดียว มีความแปรปรวนต่ำที่สุด และเทรนเร็วที่สุด เราจึงเลือกชุด C
> ส่วนกราฟทางขวาตอบคำถามว่าทำไมเลือก 18 ตัว เพราะเพิ่ม feature เกินจุดนี้แล้วคะแนนไม่ขึ้นอีก"

# 👤 คนที่ 3 — หน้า 10–13 ⭐

## หน้า 10: เทียบ 5 โมเดล
> "เราไม่ได้เลือกโมเดลไว้ล่วงหน้า แต่เทียบ 5 โมเดลด้วยเงื่อนไขเดียวกันทั้งหมด คือ feature ชุดเดียวกัน Pipeline เดียวกัน และ Stratified 5-Fold Cross-Validation บน train set เดียวกัน
> ผลคือ **Random Forest ได้ F1 สูงสุดที่ 0.842** ตามด้วย HistGradientBoosting ที่ 0.811
> จุดที่อยากให้สังเกตคือคอลัมน์ขวาสุด **Decision Tree มีช่องว่างระหว่างคะแนน train กับ CV ถึง 0.203** แปลว่าจำข้อมูลเก่งแต่ทำนายของใหม่ไม่แม่น ซึ่งเป็นปัญหา Overfitting ของต้นไม้ต้นเดียว
> Random Forest แก้ปัญหานี้ด้วยการสร้างต้นไม้ 300 ต้นแล้วโหวตกัน ความผิดพลาดของแต่ละต้นจึงหักล้างกันเอง"

## หน้า 11: เลือก Metric
> "ย้อนกลับมาเรื่องตัวชี้วัด เราไม่ใช้ Accuracy เพราะการทายว่าไม่ยกเลิกทุกรายการก็ได้ 62.9% แล้ว แต่ F1 จะเท่ากับ 0 คือจับคนที่จะยกเลิกไม่ได้เลยสักราย
> เราจึงพิจารณาจากต้นทุนของการทำนายผิดทั้ง 2 แบบ
> **แบบแรก ไม่เตือนแต่ลูกค้ายกเลิกจริง** ห้องจะว่างและขายต่อไม่ทัน เสียรายได้
> **แบบที่สอง เตือนว่าจะยกเลิกแต่ลูกค้ามาจริง** ถ้าโรงแรมรับจองเกินไว้แล้วก็จะห้องไม่พอ เสียชื่อเสียง
> ทั้งสองแบบเจ็บพอกัน เราจึงใช้ **F1-score เป็นตัวชี้วัดหลัก** เพราะจะสูงได้ก็ต่อเมื่อทั้ง Precision และ Recall ดีพร้อมกัน เสริมด้วย ROC-AUC และ PR-AUC"

## หน้า 12: ก่อน–หลัง Tuning
> "เราปรับ Hyperparameter 2 ขั้น คือ RandomizedSearch สุ่ม 20 ชุดค่าเพื่อหาบริเวณที่ดี แล้วตามด้วย GridSearch ค้นละเอียดรอบค่านั้น
> ผลที่ได้น่าสนใจครับ/ค่ะ **F1 ของ Random Forest แทบไม่ขึ้นเลย จาก 0.8422 เป็น 0.8419**
> แต่ถ้าดูคอลัมน์ขวา **ช่องว่าง train–CV แคบลงจาก 0.152 เหลือ 0.122** แปลว่าโมเดลจำข้อมูลน้อยลงและมีเสถียรภาพมากขึ้น
> เราจึงสรุปว่า tuning ในงานนี้ให้ประโยชน์ด้านการลด Overfitting มากกว่าการเพิ่มคะแนน ซึ่งเป็นเรื่องปกติของโมเดลกลุ่ม Ensemble ที่ค่าเริ่มต้นดีอยู่แล้ว
> ส่วนกราฟทางขวาคือ Validation Curve ใช้อธิบายว่าเราเลือกค่า max_depth จากตรงไหน"

## หน้า 13: Threshold + ผลบน Test
> "นอกจาก Hyperparameter เรายังปรับค่า Threshold ด้วย ปกติโมเดลใช้ 0.5 แต่ไม่จำเป็นต้องดีที่สุดเสมอไป
> เราหาค่าที่ให้ F1 สูงสุดจาก out-of-fold predictions บนชุด train ได้ **0.46** ซึ่งทำให้ **Recall เพิ่มขึ้น 2.6 จุด**
> พูดง่ายๆ คือยอมเตือนผิดเพิ่มอีก 252 ครั้ง เพื่อจับการยกเลิกที่เคยพลาดได้เพิ่ม 229 ครั้ง
> สุดท้ายเราเปิดใช้ test set 23,842 แถวเพียงครั้งเดียว ได้ **F1 0.8469 · Precision 0.8351 · Recall 0.8590 · ROC-AUC 0.9567**
> ย้ำว่าการเลือก feature เลือกโมเดล tuning และหา threshold ทั้งหมดใช้ Cross-Validation บน train เท่านั้น ไม่ได้แตะ test set เลย"

# 👤 คนที่ 4 — หน้า 14–17

## หน้า 14: Random vs Time split ⭐
> "หน้านี้เป็นข้อค้นพบที่เราคิดว่าสำคัญที่สุดครับ/ค่ะ
> การสุ่มแบ่งข้อมูลทำให้ชุด train กับ test คละช่วงเวลากัน แต่ในการใช้งานจริงโมเดลต้องทำนาย**อนาคต**จากข้อมูล**อดีต** เราจึงทดสอบอีกแบบคือแบ่งตามลำดับเวลา
> ผลคือ **F1 ตกจาก 0.8469 เหลือ 0.7249** หายไปถึง 0.12
> สาเหตุคือชุดทดสอบตามเวลามีอัตราการยกเลิก 40.99% ขณะที่ชุดฝึกมีแค่ 36.09% แสดงว่า**พฤติกรรมลูกค้าเปลี่ยนไปตามเวลาจริง**
> เราจึงสรุปว่าการสุ่มแบ่งข้อมูลประเมินโมเดลสูงเกินจริง และรายงานตัวเลขทั้งสองแบบไว้ในรายงาน"

## หน้า 15: Deploy
> "เรานำโมเดลไปทำเป็นเว็บแอปด้วย Streamlit ผู้ใช้กรอกรายละเอียดการจอง ระบบจะคำนวณ feature ที่เหลือให้เองแล้วแสดงความเสี่ยงทันที
> ตัวอย่างจริง 3 เคส จองล่วงหน้า 300 วันแบบ Non Refund กลุ่ม Groups ได้ความเสี่ยงเกือบ 100% ส่วนจองล่วงหน้า 5 วันผ่าน Direct ที่เป็นลูกค้าเก่า ได้แค่ 0.6%
> ข้อจำกัดคือโมเดลบนเว็บเป็น Random Forest ฉบับย่อขนาด 28.8 MB แทนตัวเต็มที่ 356.8 MB เพราะบริการโฮสต์ฟรีจำกัดหน่วยความจำไว้ 1 GB โดยเสีย F1 ไปเพียง 0.0093"

## หน้า 16: สรุป
