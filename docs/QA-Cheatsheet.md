โครงการตอบที่ดี: **ตอบตรงคำถามก่อน → ยกตัวเลขหนุน 1 ตัว → ปิดด้วยเหตุผล** แล้วหยุด อย่าพูดยาว

## 🔥 กลุ่มที่ถูกถามบ่อยที่สุด (เตรียมให้แม่น)

### 1. "Tuning แล้ว Random Forest ไม่ดีขึ้นเลย ทำไมยังเลือก?"
> "F1 เท่าเดิมจริงครับ/ค่ะ จาก 0.8422 เป็น 0.8419 ซึ่งน้อยกว่าค่า std แต่ **ช่องว่าง train–CV ลดจาก 0.152 เหลือ 0.122** แปลว่าโมเดลจำข้อมูลน้อยลงและเสถียรขึ้น เราจึงถือว่า tuning ได้ผลในแง่ลด Overfitting ไม่ใช่เพิ่มคะแนน"

### 2. "RF overfit อยู่ แล้วใช้ Feature Importance ของมันได้ยังไง?"
> "เราตั้ง `min_samples_leaf=5` ตอนหา importance ช่องว่างจึงเหลือแค่ **0.072** ต่ำกว่าโมเดลที่ใช้ทำนายจริงด้วยซ้ำ และเรารันซ้ำด้วยพารามิเตอร์ที่ tune แล้ว **ได้อันดับสอดคล้องกันที่ Spearman 0.985 Top-18 ตรงกัน 16 ตัว** อีกทั้ง RF เป็นแค่ 1 ใน 3 เสียง โดยมี Permutation Importance ที่วัดบน validation set เป็นตัวถ่วงครับ/ค่ะ"

**[ทำ]** เปิดสไลด์สำรอง `5_rf_importance_tuned_vs_default.png`

### 3. "ทำไมไม่ใช้ Accuracy?"
> "เพราะข้อมูลไม่สมดุล 37 ต่อ 63 ครับ/ค่ะ ถ้าทายว่าไม่ยกเลิกทุกรายการจะได้ Accuracy 62.9% แต่ F1 เท่ากับ 0 คือจับคนที่จะยกเลิกไม่ได้เลย เราจึงใช้ F1 ที่บังคับให้ทั้ง Precision และ Recall ต้องดีพร้อมกัน"

### 4. "ทำไม Feature Set C ไม่ดีกว่า B ทั้งที่คัดเลือกมาแล้ว?"
> "ผลต่างแค่ 0.0015 ซึ่งน้อยกว่าค่า std ที่ 0.0042 จึงถือว่าเท่ากันครับ/ค่ะ แต่ชุด C ใช้ตัวแปรครึ่งเดียว มีความแปรปรวนต่ำสุด และเทรนเร็วกว่า เป้าหมายของการคัดเลือกคือ**ทำให้โมเดลเรียบง่ายขึ้นโดยไม่เสียประสิทธิภาพ** ซึ่งเราทำได้"

### 5. "ทำไมต้องใช้ 3 วิธีคัดเลือก feature?"
> "เพราะแต่ละวิธีมีจุดอ่อนต่างกันครับ/ค่ะ Random Forest Importance เข้าข้างตัวแปรที่มีค่าหลากหลาย ส่วน Mutual Information มองทีละตัวแปรไม่เห็นการทำงานร่วมกัน การโหวตจึงทำให้ได้ feature ที่หลายมุมมองเห็นตรงกัน"

### 6. "เอาไปใช้กับโรงแรมไทยได้ไหม?"
> "โครงสร้างปัญหาเหมือนกันครับ/ค่ะ แต่ต้องเทรนใหม่ด้วยข้อมูลของไทย เพราะข้อมูลชุดนี้มาจากโปรตุเกสปี 2015–2017 และผลจาก time split ก็ชี้อยู่แล้วว่าพฤติกรรมเปลี่ยนตามเวลา ต้องเทรนใหม่เป็นระยะ"

| คำถาม | คำตอบสั้น |
|---|---|
| "แถวซ้ำ 31,994 แถวทำไมไม่ลบ?" | ชุดข้อมูลไม่มีรหัสการจอง กรุ๊ปที่จองหลายห้องพร้อมกันจึงดูเหมือนซ้ำ เราเก็บไว้และระบุเป็นข้อจำกัดว่าอาจทำให้ random split ดูดีเกินจริง (ถ้าลบจะเหลือ 87,228 แถว และอัตรายกเลิกเปลี่ยนเป็น 27.5%) |
| "Data Leakage คืออะไร รู้ได้ไงว่าคอลัมน์นั้น leak?" | คือข้อมูลที่ไม่มีทางรู้ตอนทำนายจริง หลักฐานของเราคือการจองที่ถูกเปลี่ยนห้องมีอัตรายกเลิก 0% แปลว่ารู้หลังเช็คอิน |
| "ข้อมูลเก่าตั้งแต่ 2015–2017 ยังใช้ได้ไหม?" | โครงสร้างปัญหายังเหมือนเดิม แต่ไม่ครอบคลุมผลกระทบจาก COVID-19 ที่เปลี่ยนนโยบายยกเลิก เราระบุเป็นข้อจำกัดไว้แล้ว |
| "ทำไมเลือก Random Forest?" | ไม่ได้เลือกล่วงหน้า แต่เทียบ 5 โมเดลด้วยเงื่อนไขเดียวกัน RF ได้ F1 สูงสุด 0.842 และเหมาะกับข้อมูลตารางที่มีความสัมพันธ์ไม่เป็นเส้นตรง |
| "Threshold 0.46 มายังไง ทำไมไม่ใช้ 0.5?" | หาจาก out-of-fold predictions บนชุด train ไม่ได้ใช้ test set เลือกค่าที่ให้ F1 สูงสุด ผลคือ Recall เพิ่ม 2.6 จุด |
| "จัดการข้อมูลไม่สมดุลยังไง ทำไมไม่ใช้ SMOTE?" | ใช้ `class_weight='balanced_subsample'` ถ่วงน้ำหนักในตัวโมเดล ซึ่งไม่สร้างข้อมูลปลอมเพิ่มเหมือน SMOTE จึงไม่เสี่ยงบิดเบือนการกระจายของข้อมูลจริง |
| "โมเดลบนเว็บกับในรายงานเป็นตัวเดียวกันไหม?" | เป็นชนิดเดียวกันคือ Random Forest แต่บนเว็บย่อขนาดเหลือ 28.8 MB (150 ต้น) เพราะบริการฟรีจำกัด RAM 1 GB โดยเสีย F1 ไปแค่ 0.0093 |
| "ถ้าโรงแรมเอาไปใช้จริง ได้ประโยชน์อะไร?" | จัดลำดับความเสี่ยงของการจอง เพื่อกำหนดนโยบายมัดจำ ยืนยันการเข้าพักล่วงหน้า หรือวางแผน Overbooking ให้แม่นขึ้น แทนการทำแบบเหมารวมทุกการจอง |
